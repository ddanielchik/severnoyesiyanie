# Северное сияние — Cocktail Bar Backend

**Лабораторная работа №1 — разработка монолитного приложения на Spring Boot**

## 1. Описание проекта

**«Северное сияние»** — серверное приложение для автоматизации работы коктейльного бара.

Система предназначена для управления посетителями, коктейльным меню, посещениями и заказами. Дополнительно реализован механизм персональных рекомендаций напитков на основе вкусовых предпочтений гостей.

Проект разрабатывается на языке **Kotlin** с использованием **Spring Boot** и представляет собой монолитное REST API-приложение.

Основная цель лабораторной работы — разработать серверную часть информационной системы с использованием современных подходов к проектированию, реляционной базы данных, транзакций, контейнеризации и автоматизированного тестирования.

## 2. Предметная область и роли пользователей

В системе предусмотрены три роли пользователей.

### CLIENT — посетитель

Посетитель является гостем коктейльного бара. С его учётной записью связываются посещения заведения.

Для посещения можно указать номер столика, задать вкусовые предпочтения и получить рекомендации коктейлей.

### WAITER — официант

Официант отвечает за оформление заказов посетителей.

При создании заказа система проверяет, что указанный сотрудник действительно имеет роль `WAITER`.

### WORKER — работник бара

Работник бара отвечает за приготовление заказанных напитков.

При оформлении заказа система проверяет, что назначенный сотрудник имеет роль `WORKER`.

Роли представлены перечислением `UserRole` и хранятся в базе данных как строки.

> На текущем этапе роли используются в модели данных и бизнес-проверках. Полноценная аутентификация и разграничение доступа к API по ролям не реализованы.

## 3. Основные функциональные возможности

### Управление пользователями

- Создание пользователей.
- Получение информации о пользователях.
- Обновление пользовательских данных.
- Удаление пользователей.
- Назначение одной из трёх ролей: `CLIENT`, `WAITER`, `WORKER`.

### Управление коктейльным меню

- Добавление новых коктейлей.
- Получение информации о коктейлях.
- Редактирование и удаление позиций меню.
- Указание названия, цены и вкусовых характеристик напитка.
- Получение списка коктейлей с пагинацией.

Коктейли могут иметь несколько вкусовых тегов, например `SWEET`, `SOUR`, `BITTER`, `SALTY` и `SPICY`.

### Управление посещениями

- Открытие посещения для клиента.
- Привязка посещения к пользователю.
- Указание и изменение номера столика.
- Сохранение времени открытия посещения.
- Изменение временных вкусовых предпочтений.
- Закрытие посещения с фиксацией времени завершения.
- Автоматическая очистка временных предпочтений при закрытии.

История посещений сохраняется в базе данных.

### Рекомендации коктейлей

Для открытого посещения предусмотрен отдельный сервис рекомендаций — `RecommendationService`.

Он сравнивает вкусовые предпочтения посетителя с тегами коктейлей и формирует список подходящих напитков.

Рекомендации связаны с текущим посещением, а не с постоянным профилем пользователя.

### Управление заказами

- Создание заказа для открытого посещения.
- Добавление нескольких коктейлей в один заказ.
- Указание количества каждого напитка.
- Назначение официанта и работника бара.
- Проверка ролей назначенных сотрудников.
- Автоматический расчёт общей стоимости заказа.
- Сохранение цены каждого коктейля на момент оформления.
- Получение ранее созданного заказа по идентификатору.

Сохранение цены в `OrderItem.unitPrice` позволяет корректно отображать старые заказы, даже если стоимость коктейля в меню изменилась.

## 5. Архитектура приложения

Проект реализован в виде монолитного приложения с разделением ответственности между слоями.

Основные пакеты:

```text
src/main/kotlin/ru/severnoyesiyanieBack/
├── controller/    # REST-контроллеры
├── service/       # Бизнес-логика приложения
├── repository/    # Работа с базой данных
├── entity/        # JPA-сущности
├── dto/           # Модели запросов и ответов API
└── exception/     # Пользовательские исключения и их обработка
```

**Controller** принимает HTTP-запросы, проверяет входные данные и передаёт управление сервисному слою.

**Service** содержит бизнес-правила: проверку статуса посещения, ролей сотрудников, расчёт стоимости заказа и управление транзакциями.

**Repository** предоставляет доступ к данным через Spring Data JPA.

**Entity** описывает структуру хранимых данных и связи между таблицами.

**DTO** используются для передачи данных между клиентом и сервером без прямого предоставления JPA-сущностей.

**Exception** содержит собственные исключения приложения и централизованный обработчик ошибок.

Разделение по слоям упрощает сопровождение, тестирование и расширение проекта.

## 6. Модель данных и связи между сущностями

Основные сущности приложения:

| Сущность | Назначение |
|---|---|
| `User` | Пользователь системы и его роль |
| `MenuItem` | Коктейль из меню |
| `TasteTag` | Вкусовая характеристика коктейля |
| `Visit` | Посещение бара |
| `Order` | Заказ посетителя |
| `OrderItem` | Отдельная позиция заказа |

### Реализованные отношения

**One-to-Many / Many-to-One:**

- Один пользователь может иметь несколько посещений.
- Одно посещение может содержать несколько заказов.
- Один заказ содержит несколько позиций `OrderItem`.
- Каждый заказ связан с официантом и работником бара.

**Many-to-Many:**

- Один коктейль может иметь несколько вкусовых тегов.
- Один вкусовой тег может относиться к нескольким коктейлям.
- Одно посещение может иметь несколько временных вкусовых предпочтений.

**Many-to-Many с дополнительными полями:**

Связь между заказами и коктейлями реализована через отдельную сущность `OrderItem`.

Помимо ссылок на заказ и коктейль, она содержит:

- `quantity` — количество напитков.
- `unitPrice` — цена одной единицы на момент оформления.

Такой подход позволяет хранить подробную информацию о составе заказа и сохранять корректную историю стоимости.

## 7. REST API

Взаимодействие с приложением осуществляется через HTTP с использованием REST API.

Основные группы эндпоинтов:

| Группа | Назначение |
|---|---|
| Users | Управление пользователями |
| Menu | Управление коктейльным меню |
| Visits | Управление посещениями |
| Recommendations | Получение рекомендаций |
| Orders | Создание и просмотр заказов |

Примеры реализованных запросов:

```http
POST /api/orders
GET /api/orders/{id}
GET /api/visits/{id}/recommendations
```

Для HTTP-ответов используются соответствующие статусы, в том числе:

- `200 OK` — успешное получение данных.
- `201 Created` — успешное создание ресурса.
- `400 Bad Request` — некорректный запрос или нарушение валидации.
- `404 Not Found` — запрашиваемая сущность отсутствует.
- `409 Conflict` — нарушение бизнес-правил, например неправильная роль сотрудника.

Обработка пользовательских исключений централизована в `GlobalExceptionHandler`.

## 8. Валидация данных

Для контроля корректности данных используются аннотации Jakarta Bean Validation на уровне DTO и JPA-сущностей.

Примеры проверок:

- `@NotBlank` — обязательные непустые строковые поля.
- `@Email` — корректность формата электронной почты.
- `@Size` — ограничение длины строк.
- `@Positive` — положительные идентификаторы и количество напитков.
- `@DecimalMin` — ограничение минимального денежного значения.
- `@NotEmpty` — запрет создания заказа без позиций.
- `@Valid` — проверка вложенных объектов запроса.

Дополнительные ограничения целостности обеспечиваются средствами PostgreSQL: `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL` и `UNIQUE`.

## 9. Пагинация

В приложении предусмотрены два подхода к получению списков данных.

### Page — пагинация с общим количеством записей

Применяется для списка посещений.

Клиент может получать данные постранично. Общее количество записей передаётся в HTTP-заголовке:

```http
X-Total-Count: 120
```

Размер страницы ограничивается максимум 50 записями.

### Slice — бесконечная прокрутка

Применяется для коктейльного меню.

`Slice` позволяет получать данные частями и определять, существует ли следующая часть, без обязательного вычисления общего количества записей.

Это подходит для интерфейсов с бесконечной прокруткой.

> Дополнительно необходимо завершить проверку пагинации всех запросов на получение списков, включая сервис рекомендаций.

## 10. Транзакции и целостность данных

Для выполнения сложных операций используется `@Transactional`.

### Транзакция №1 — создание заказа

При оформлении заказа приложение:

1. Находит открытое посещение.
2. Проверяет его статус.
3. Проверяет существование сотрудников и соответствие их ролей.
4. Находит выбранные коктейли.
5. Рассчитывает стоимость каждой позиции и общую сумму.
6. Создаёт заказ вместе с его позициями.
7. Сохраняет результат в базе данных.

Транзакция необходима, чтобы заказ и его позиции сохранялись как единое целое. При возникновении ошибки изменения должны откатываться.

### Транзакция №2 — закрытие посещения

При закрытии посещения приложение:

1. Находит посещение.
2. Проверяет, что оно открыто.
3. Изменяет статус на `CLOSED`.
4. Записывает время закрытия.
5. Удаляет временные вкусовые предпочтения.
6. Сохраняет изменения.

Транзакция гарантирует согласованность статуса, времени закрытия и состояния предпочтений.

### Защита от конкурентных операций

Для создания заказа и закрытия посещения применяется пессимистическая блокировка:

```kotlin
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

Она предотвращает конфликт между одновременным оформлением заказа и закрытием соответствующего посещения.

Блокировка удерживается в рамках транзакции и освобождается после её завершения.

## 11. Работа с базой данных

В качестве СУБД используется PostgreSQL.

Структура базы данных создаётся и изменяется с помощью миграций **Flyway**.

Основные миграции:

- `V1__create_base_tables.sql` — создание таблиц, связей и ограничений.
- `V2` — заполнение справочников вкусовых тегов и тестового коктейльного меню.

Flyway автоматически применяет необходимые миграции при запуске приложения.

Перечисления, такие как `UserRole` и `VisitStatus`, сохраняются строками с использованием `EnumType.STRING`.

## 12. Запуск через Docker Compose

Для запуска проекта необходимы:

- Docker;
- Docker Compose.

Клонирование репозитория:

```bash
git clone https://github.com/ddanielchik/severnoyesiyanie.git
cd severnoyesiyanie
```

Сборка и запуск приложения:

```bash
docker compose up --build
```

Docker Compose запускает два сервиса:

**postgres** — контейнер с PostgreSQL 17.

**app** — контейнер со Spring Boot-приложением, собранным с помощью Maven и Java 21.

Готовность базы данных проверяется через `healthcheck`. После запуска PostgreSQL приложение подключается к ней и выполняет миграции Flyway.

Для конфигурации подключения используются переменные окружения:

```text
SPRING_DATASOURCE_URL
SPRING_DATASOURCE_USERNAME
SPRING_DATASOURCE_PASSWORD
```

После запуска приложение доступно по адресу:

`http://localhost:8080`

Интерактивная документация REST API:

`http://localhost:8080/swagger-ui/index.html`

Остановить контейнеры можно командой:

```bash
docker compose down
```

При обычной остановке данные PostgreSQL сохраняются в Docker volume.

Текущие параметры подключения предназначены для локальной учебной среды и не должны использоваться как производственные учётные данные.

## 15. Организация разработки

Для управления версиями проекта используется Git с подходом **feature branching**.

Функциональность разрабатывается в отдельных ветках:

- `feature/user` — управление пользователями и базовые модели.
- `feature/cocktail-menu` — коктейльное меню.
- `feature/visits` — управление посещениями.
- `feature/recommendations` — рекомендации напитков.
- `feature/orders` — управление заказами, транзакции и Docker-конфигурация.

Изменения объединяются через Pull Request.

Для новых коммитов используется соглашение Conventional Commits, например:

```text
feat: add cocktail recommendations
fix: validate employee roles
test: add order integration tests
docs: update README
```

При разработке используются принципы разделения ответственности, SOLID, DRY и KISS.
